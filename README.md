# 多无人机动态协同调度

使用 C++ 实现的无人机配送调度原型。通过 A* 计算航路距离，根据载重、截止时间和电量约束筛选订单，再使用评分函数进行贪心分配；没有接到订单的无人机根据区域评分前往待命。电量不高于安全值的无人机会被标记为充电状态，退出任务分配。

## 一、程序流程

```text
读取地图
读取无人机初始信息
循环：
    读取一条新订单
    获取本轮当前时间
    更新已完成任务的无人机位置和状态
    将电量不高于安全值的无人机标记为 TO_CHARGE
    为 IDLE 无人机分配订单
    为剩余 IDLE 无人机分配待命区域
```

每输入一条订单，触发一轮调度。此前尚未分配的订单也会参与本轮分配。

## 二、数据结构

### 1. 坐标 `$Point`

`x`、`y` 保存二维坐标，用于地图节点、无人机位置和订单的取送货点。

### 2. 订单 `$Order`

| 字段 | 含义 |
| --- | --- |
| `id` | 订单编号，从 1 递增 |
| `pickup` | 取货点坐标 |
| `delivery` | 送达点坐标 |
| `deadLine` | 最晚完成配送的时间 |
| `weight` | 货物重量 |
| `assigned` | 是否已分配 |

`assigned` 表示是否已经分配，不表示是否已经送达。历史订单保留在 `orders` 中。

### 3. 无人机 `$Drone`

| 字段 | 含义 |
| --- | --- |
| `id` | 无人机编号，按输入顺序生成 |
| `location` | 当前记录的位置 |
| `maxWeight` | 最大载重 |
| `battery` | 剩余电量 |
| `status` | 当前状态 |
| `doneTime` | 当前任务预计完成时间 |
| `taskLocation` | 当前任务结束位置 |

状态包括：

| 状态 | 当前代码中的作用 |
| --- | --- |
| `IDLE` | 空闲，可以接单或前往待命区域 |
| `DELIVERY` | 配送中，不参与新订单分配 |
| `TO_SPOT` | 前往待命点，不参与新订单分配 |
| `TO_CHARGE` | 低电量停派状态，不参与订单分配和待命调度 |

位置不会在飞行过程中连续更新，而是在任务结束后的状态检查中直接更新为 `taskLocation`。

## 三、主要参数

| 参数 | 当前值 | 含义 |
| --- | --- | --- |
| `TIME_FOR_PICKUP` | 100 | 取货耗时，秒 |
| `TIME_FOR_OFFLOAD` | 100 | 卸货耗时，秒 |
| `DRONE_SPEED` | 8 | 飞行速度，米/秒 |
| `BATTERY_USED_PER_M` | 0.01 | 每米飞行耗电量 |
| `SAFETY_BATTERY` | 5.0 | 安全电量阈值 |
| `falpha`、`fbeta`、`fgamma` | 0.5、0.2、0.3 | 订单评分权重 |
| `galpha`、`gbeta`、`ggamma` | 0.5、0.3、0.2 | 区域评分权重 |

电量输入与耗电系数使用相同量纲，代码没有限定必须使用百分比。

**评分权重均为暂定值。**这些数值只是为 `const` 常量提供初始值，尚未经过实验验证。后续需要对指标进行归一化，并通过更多数据比较订单完成率、平均配送时间和总耗电量，确定较合理的参数。当前代码尚未实现归一化。

## 四、地图与 A* 路径搜索

### 1. 坐标映射与建图

`getId()` 将坐标映射为整数节点编号：

- `hashId`：坐标到编号。
- `realId`：编号到坐标。
- `g`：图的邻接表，保存相邻节点和边权。

`mapInit()` 读取每条航路的两个端点和长度，分别添加正向、反向边，因此地图为无向带权图。

坐标采用浮点数精确匹配。无人机初始位置、取货点和送达点应与已录入的地图节点坐标一致，程序不会自动寻找最近节点。

### 2. 距离计算

`astar(a,b)` 返回两点之间的航路距离。起终点不在地图中或两点不可达时，返回 `-1`。

优先队列按以下估价值选择待扩展节点：

$$
F(u)=\operatorname{dist}(u)+h(u,t)
$$

其中 `dist[u]` 是当前已发现的起点到节点 `u` 的最小距离，启发函数为欧几里得距离：

$$
h(u,t)=\sqrt{(x_u-x_t)^2+(y_u-y_t)^2}
$$

为保证最短路结果，边权应为非负航路长度，且不小于两个端点的直线距离，使启发函数不会高估剩余距离。若输入边权不满足这一条件，可将启发值设为 0，改为 Dijkstra 搜索。

函数只返回距离，没有保存或输出路径节点序列。

## 五、订单分配

### 1. 计算候选任务

程序依次遍历无人机，只处理 `IDLE` 状态；对于每架无人机，遍历尚未分配的订单。

先检查载重，再通过两次路径搜索计算：

$$
d_1=\operatorname{distance}(\text{无人机位置},\text{取货点})
$$

$$
d_2=\operatorname{distance}(\text{取货点},\text{送达点}),\qquad d=d_1+d_2
$$

任意一段不可达，则跳过该订单。

### 2. 时间与电量检查

任务耗时包括飞行、取货和卸货：

$$
T=\text{TIME\_FOR\_PICKUP}+\frac{d}{\text{DRONE\_SPEED}}+\text{TIME\_FOR\_OFFLOAD}
$$

设订单截止时间为 $D$，本轮当前时间为 $t$，则时间裕量为：

$$
s=D-t-T
$$

`s < 0` 表示立即出发也无法按时完成，跳过该订单。

预计耗电量为：

$$
E=d\times\text{BATTERY\_USED\_PER\_M}
$$

要求：

$$
\text{battery}-E\geq\text{SAFETY\_BATTERY}
$$

当前模型只计算飞行耗电，不包含取货、卸货期间的耗电，以及配送后前往充电点所需的电量。

### 3. 评分与选择

对满足约束的候选订单计算：

$$
f(i,j)=\frac{\alpha_f}{1+d}+\frac{\beta_f}{1+s}+\frac{\gamma_f}{1+E}
$$

- 距离越短，距离项越高。
- 时间裕量越小，紧迫程度项越高。
- 耗电越少，能耗项越高。

候选项存入 `fs`，包含评分、无人机编号、订单编号和任务耗时。排序后选择评分最高的候选项。评分完全相同时，当前存储结构会优先选择编号较大的订单。

分配后执行：

1. 将订单标记为已分配。
2. 将无人机状态改为 `DELIVERY`。
3. 设置 `doneTime = now + T`。
4. 设置 `taskLocation` 为送达点。
5. 一次性扣除预计飞行耗电量。

这是逐架贪心分配，先处理的无人机先选订单，并非将全部“无人机—订单”组合统一排序。因此结果可能受无人机遍历顺序影响。

### 4. 起飞时间

当前采用分配后立即出发的规则：

$$
t_{\text{start}}=\text{now},\qquad t_{\text{finish}}=\text{now}+T
$$

没有单独搜索最佳起飞时刻，也没有处理起降间隔和航路冲突。同一轮分配使用同一个 `now`。

例如，总航程为 800 米，则任务耗时为 $100+800/8+100=300$ 秒，耗电量为 8。若截止时间为当前时刻后 400 秒，则时间裕量为 100 秒。

## 六、空闲无人机的待命调度

### 1. 地图分块

`mapX`、`mapY` 记录地图节点的最大横纵坐标。网格边长为：

$$
\text{blockX}=\max(1,\sqrt{\text{mapX}}),\qquad
\text{blockY}=\max(1,\sqrt{\text{mapY}})
$$

根据坐标除以网格边长得到区域下标。当前划分按非负坐标场景设计，没有使用最小坐标平移地图。

`spot[i][j]` 保存区域代表节点：按节点编号遍历时，第一个落入该区域的节点被选为待命点。没有地图节点的区域不参与选择。

### 2. 区域统计与评分

对每架没有接到订单的空闲无人机，统计：

- `q[i][j]`：该区域累计录入订单的取货点数量，包含已分配订单。
- `n[i][j]`：其他空闲无人机的当前位置，以及前往待命区域的无人机目标位置，落在该区域内的数量。
- `d`：当前无人机到区域代表节点的航路距离。

配送中和充电状态的无人机不计入 `n`。

排除不可达或到达后电量低于安全值的区域，再计算：

$$
g(i,k)=\alpha_gq_k+\frac{\beta_g}{1+n_k}+\frac{\gamma_g}{1+d_{ik}}
$$

选择最高分区域后，将状态改为 `TO_SPOT`，保存目标位置，扣除预计飞行耗电量，并设置：

$$
\text{doneTime}=\text{now}+\frac{d}{\text{DRONE\_SPEED}}
$$

每安排一架无人机，后续无人机会重新统计分布，因此能够将此前安排的无人机计入对应区域。

## 七、低电量与充电状态

每轮状态更新中新增了以下判断：

```cpp
if (drone.battery <= SAFETY_BATTERY) {
    drone.status = "TO_CHARGE";
}
```

电量不高于安全阈值时，无人机进入 `TO_CHARGE`。后续订单分配和待命调度都只处理 `IDLE`，因此该无人机会停止接单和待命移动。

**当前实现的是充电状态标记。**程序尚未定义充电点、前往充电点的路径、充电耗时、电量恢复，以及充满后返回 `IDLE` 的流程。进入 `TO_CHARGE` 后，当前代码没有自动退出该状态的逻辑。

还需要注意两个边界：

- 该判断对所有状态生效。电量在任务分配时已经提前扣除，如果扣除后恰好等于安全值，下一轮输入可能在任务结束前将 `DELIVERY` 或 `TO_SPOT` 改为 `TO_CHARGE`，影响后续的位置更新。完善时应区分任务中和任务完成后的充电处理。
- 电量高于安全值、但不足以执行某个订单时，只会跳过该订单，不会因此自动进入充电状态。

## 九、输入与输出

### 输入格式

```text
航路数量 M
端点1_x 端点1_y 端点2_x 端点2_y 航路长度
……共 M 条

无人机数量 K
位置_x 位置_y 最大载重 剩余电量
……共 K 架

取货点_x 取货点_y 送达点_x 送达点_y 截止时间戳 货物重量
……每输入一条订单，触发一轮调度
```

地图距离按米、时间按秒理解。重量使用统一单位即可。

`getCurrentTime()` 使用 `system_clock` 的纪元秒数，常见环境下为 Unix 时间戳。因此截止时间也需要使用相同时间基准，不能直接填写“剩余 600 秒”。

### 输出格式

分配订单：

```text
DRONE: 1-> ORDER: 2
```

前往待命区域：

```text
DRONE: 3-> SPOT: 0,1
```

`SPOT` 后是网格下标，不是目标点坐标。订单分配的输出语句目前没有换行，多条信息可能连在一起；低电量状态变化没有单独输出。程序也尚未输出起飞时间和预计完成时间。

## 十、运行边界与改进方向

- **调度触发：**仅输入新订单时更新状态，没有新输入就不会自动处理任务完成或再次分配。
- **任务模型：**一次执行一个订单，不支持多单合送、配送中接单或待命途中改道。
- **充电流程：**目前只有状态标记，需要继续补充充电点选择、可达电量检查、充电完成和恢复接单。
- **评分设置：**权重尚未验证，指标尚未归一化；距离和能耗在当前线性电量模型下也存在相关性。
- **需求统计：**待命评分使用累计订单数，可以改为近期时间窗口内的订单数。
- **计算开销：**多次重复运行 A*，可缓存不变地图上的距离，尤其是同一订单取货点到送达点的距离。
- **数据范围：**邻接表大小为 100000，节点编号从 1 开始，因此节点数量应小于 100000；输入还需满足坐标、边权等基本约束。
- **编译兼容性：**`$Point` 等名称依赖编译器对 `$` 标识符的扩展支持，改为 `Point`、`Order`、`Drone` 可提高可移植性。

后续可通过不同订单分布和无人机配置进行模拟，比较订单完成率、平均配送时间、总航程和总耗电量，再调整权重与分配策略。本文按源码逻辑说明，未提供运行实验或性能测试结果。
