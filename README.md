# main.cpp 代码讲解

本文对应同目录下使用 **cin/cout、Tab 缩进、传统 C++ 写法**的 `main.cpp`。按实际代码解释，没有额外引入代码中尚未实现的功能。

## 一、先看懂程序在做什么

程序维护一批订单和无人机。出现新订单、无人机完成配送或充电等情况时，重新做一次调度：

1. 有合适订单，就按 f 函数选出最好的“无人机—订单”组合。
2. 每选中一对，立即把订单标为已分配，无人机标为配送中，再选下一对。
3. 剩余空闲无人机如果需要补电，就去充电；否则按 g 函数选择待命区域。
4. 时间直接跳到下一个事件发生的时刻，然后重复。

其中，A\* 负责找路，f 负责选订单，g 负责选待命区域，事件队列负责推进时间。

建议第一次阅读时先看 `main()` 的事件循环、`assignOrders()`、`evaluate()`，再回头看 A* 和位置更新细节。

## 三、几个结构体分别存什么

### 1. Point：三维坐标

```cpp
struct Point {
	double x, y, z;
	Point(double a = 0, double b = 0, double c = 0) {
		x = a;
		y = b;
		z = c;
	}
};
```

里面的 `Point(...)` 是构造函数：创建一个点时，给它设置坐标。

例如 `Point(1, 2, 3)` 表示坐标 `(1, 2, 3)`；直接写 `Point p;` 时，三个坐标默认都是 0。

初始位置、取货点和送达点都是整数格点，但无人机飞到一条边中间时，坐标可能是小数，所以使用 `double`。

### 2. Path：空间路线

| 字段 | 含义 |
|---|---|
| `p` | 路线经过的点，按起点到终点排列 |
| `len` | 整条路线的长度 |

`vector<Point>` 可以理解成一个长度能够变化的点数组。`push_back()` 向末尾加一个点，`size()` 返回当前点数。

`Path()` 把长度设为 `INF`。A* 如果找不到路，就返回这个默认对象；找到路后才填入实际长度和点序列。

### 3. Leg：带时间的一个小段

| 字段 | 含义 |
|---|---|
| `a`、`b` | 这一段的起点、终点 |
| `begin`、`end` | 这一段开始、结束的绝对时刻 |

`Path` 只回答“经过哪些点”；`Leg` 还回答“什么时候经过”。

例如从 `(0,0,0)` 飞到 `(1,0,0)`，时间是 3 到 4 秒，就可以存为一个 `Leg`。取货和卸货也可以存成 `Leg`，只是它们的 `a` 和 `b` 相同。

### 4. Order：订单

| 字段 | 含义 |
|---|---|
| `id` | 订单编号，按输入顺序从 1 开始 |
| `pickup`、`delivery` | 取货点、送达点 |
| `deadline` | 最晚送达时刻，包含卸货时间 |
| `weight` | 订单重量 |
| `assigned` | 是否已经分给某架无人机 |
| `arrival` | 订单进入系统的时刻 |
| `takeoff` | 无人机开始执行这张订单的时刻 |
| `finish` | 订单实际完成时刻 |

`takeoff`、`finish` 初始设为 -1。订单被分配时填写 `takeoff`，收到配送完成事件时填写 `finish`。

注意：`assigned=true` 表示已经分配，不等于已经送达。已经送达的订单也继续保持这个标记，避免再次分配。

### 5. Drone：无人机

| 字段 | 含义 |
|---|---|
| `id` | 无人机编号 |
| `position` | 当前真实位置 |
| `maxLoad` | 最大载重 |
| `battery`、`capacity` | 当前电量、电池容量 |
| `state` | 当前状态 |
| `taskFinishTime` | 当前任务阶段的预计结束时刻 |
| `version` | 当前任务的版本号，用于识别失效事件 |
| `target` | 正在前往的待命区域编号；0 表示没有 |
| `settled` | 是否已经安置在待命点，暂时不需要再搬家 |
| `legs` | 当前任务的全部飞行和服务时间段 |

`taskFinishTime` 可能表示配送完成、抵达待命点、抵达充电点或充满电的时刻，取决于当前状态。

`State` 用 `enum` 给状态起名字，避免直接写含义不清楚的数字：

| 状态 | 含义 |
|---|---|
| `IDLE` | 空闲，可以接单 |
| `DELIVERY` | 正在配送 |
| `TO_CHARGER` | 正在去充电点 |
| `CHARGING` | 正在充电 |
| `TO_HOTSPOT` | 正在去待命点，可以改道接单 |
| `GROUNDED` | 无法安全到达充电点，停飞 |

### 6. Region：待命区域

`xmin/xmax/ymin/ymax` 表示区域在平面上的范围，`standby` 表示指定待命点。区域归属不看高度，待命点本身仍然有三维坐标。

### 7. Event 和 EventCmp：事件及其先后顺序

`Event` 保存事件发生时刻、事件类型、相关无人机编号、订单编号和任务版本号。

事件类型包括：

| 类型 | 发生了什么 |
|---|---|
| `ARRIVAL` | 新订单到达 |
| `FINISH` | 配送完成 |
| `REACH_CHARGER` | 抵达充电点 |
| `CHARGED` | 充满电 |
| `REACH_HOTSPOT` | 抵达待命点 |

```cpp
bool operator()(Event a, Event b) const {
	return a.time > b.time;
}
```

这是给优先队列使用的比较规则。它让时间大的事件优先级更低，所以 `events.top()` 总是最早发生的事件。`operator()` 由优先队列自动调用。

### 8. Node 和 NodeCmp：A* 搜索节点

`Node.id` 是地图格点编号，`Node.f` 是 A* 的搜索估价：

```text
已走距离 + 当前点到目标的直线距离
```

`NodeCmp` 让估价更小的点先被搜索。这里的 `Node.f` 与订单分配的 f 公式是两件事，只是都采用了常见的 f 命名。

## 四、全局变量与基础函数

### 1. 全局数组和初始化

`order[]`、`drone[]`、`region[]`、`charger[]` 分别保存订单、无人机、区域和充电点，下标从 1 开始。

`blocked[]` 表示地图格点是否被阻塞；`dis[]` 保存 A* 当前找到的最短距离；`pre[]` 保存路径上前一个格点的编号。

这些对象是全局对象，未显式赋值的数值和布尔字段初始为 0。例如 `assigned=false`、`state=IDLE`、`version=0`、`now=0`。因此代码里没有再逐个清零。如果以后改成函数里的局部对象，就不能继续依赖这种初始化方式。

| 变量 | 含义 |
|---|---|
| `X/Y/Z` | 地图三个方向的格点数 |
| `B/C/R/N/M` | 禁飞格、充电点、区域、无人机、订单的数量 |
| `now` | 当前仿真时刻 |
| `horizon` | 仿真截止时刻 |
| `energyUsed` | 所有无人机已经消耗的飞行电量 |
| `events` | 尚未处理的事件优先队列 |

### 2. readPoint 和 distance3

`readPoint(Point &p)` 读入三个坐标。`&` 表示引用，因此函数修改的是传进来的那个点。

`distance3(a,b)` 计算三维直线距离：

```text
sqrt((ax-bx)² + (ay-by)² + (az-bz)²)
```

直线距离用于 A* 的启发值和相邻路径点之间的线段长度；无人机到取货点的总距离仍然要通过 A* 找路，不能直接忽略障碍。

### 3. id 和 point

程序把三维地图压成一维数组：

```cpp
int id(int x, int y, int z) {
	return (z * Y + y) * X + x;
}
```

x 方向每走一格，编号加 1；y 方向每走一格，加 X；z 方向每走一格，加 X×Y。

`point(u)` 做相反的事，把一维编号还原为三维坐标。这样 `blocked[]`、`dis[]`、`pre[]` 都只需要一维数组。

### 4. valid、inside 和 snap

- `valid(x,y,z)`：判断格点是否在地图内且没有被阻塞。
- `inside(p,k)`：判断点 p 的 x/y 是否在区域 k 内，包含边界。
- `snap(x)`：如果 x 已经非常接近整数，就修正为整数，避免把 `2.999999999` 当成真实的边中间位置。

`dx[]/dy[]/dz[]` 列出六个方向：左右、前后、上下。代码没有斜向飞行边，所以不会斜穿障碍格。

## 五、astar：怎样找到避开障碍的路线

### 1. 初始化

每次搜索先把所有 `dis` 设为 `INF`，`pre` 设为 -1，建立一个估价最小的点优先弹出的队列。

### 2. 处理起点在边中间的情况

无人机在去热点途中可能飞到了 `(2.4,3,0)`，这不是整数格点。

代码用 `floor` 和 `ceil` 找到所在边的两个端点 `(2,3,0)`、`(3,3,0)`，把它们同时作为搜索起点，初始距离分别为 0.4 和 0.6。这就可以比较“先掉头”和“继续前进”两种路线。

这种处理依赖本程序的运动规则：无人机沿六邻接栅格边飞行，所以非整数位置最多只有一个坐标不是整数。它不是对任意三维小数点都能直接这样连接。

### 3. 不断取出当前最值得搜索的点

每次从 q 取出最小估价节点 u，尝试六个相邻格点 v。如果不越界也不是障碍，而且经过 u 的路线更短：

```cpp
if (dis[u] + 1 < dis[v]) {
	dis[v] = dis[u] + 1;
	pre[v] = u;
	q.push(Node(v, dis[v] + distance3(point(v), goal)));
}
```

这里加 1，是因为相邻整数格点的边长就是 1。`pre[v]=u` 表示“到 v 的这条更短路线，前一步在 u”。

队列里可能保留同一点的旧记录。`top.f > dis[u] + distance3(p,goal) + EPS` 就是在跳过已经过时的记录。

### 4. 到达终点后还原路线

从终点沿 `pre[]` 一直往回找，得到的是倒序点列；用 `reverse()` 翻转后，才是起点到终点的路线。如果真实起点位于边中间，再把它插入路线最前面。

如果队列都空了还没到终点，就返回 `Path()`，其中 `len=INF`，表示不可达。

在这个固定六邻接地图上，直线距离不会高估剩余路径长度，所以 A* 可以找到最短距离路线。但这只是**地图上的最短路**，不是整个无人机调度问题的全局最优。

## 六、与路线、任务、事件有关的辅助函数

### 1. nearestCharger

从指定点到每个充电点都跑一次 A*，返回最短的可达路线。这里按实际路径长度比较，不按直线距离。

### 2. addEvent、current 和 waiting

`addEvent(t,type,i,j)` 把事件加入队列，并记录无人机当前的 `version`。如果没有相关无人机，i 使用 0，例如订单到达事件。

`current(e)` 判断事件是否仍有效：无相关无人机的事件直接有效；否则事件版本号必须等于无人机当前版本号。

`waiting(j)` 只检查订单已经到达且未被分配。即使所有订单预先读入，未来订单也不会提前参与分配。

本版没有单独的“订单过期”状态。过期订单可能仍满足 `waiting()`，但后面的时间窗检查一定会拒绝它。

### 3. beginTask

开始新任务时：增加版本号、切换状态、清空旧轨迹，把任务结束时间先设为当前时刻，并清除旧的待命目标和待命标记。

为什么需要版本号？例如原本 10 秒抵达热点，5 秒改道接单。旧的“10 秒抵达热点”事件还在队列里，如果照常执行，就会错误地把配送中的无人机变为空闲。增加版本号后，`current()` 会把这个旧事件忽略。

### 4. fly 和 service

`fly(i,path)` 把空间路线转换成带时间的连续小段，追加到无人机 i 的 `legs` 中。每段的飞行时间是：

```text
这段的长度 / SPEED
```

`service(i,p)` 在位置 p 追加一个时长为 `SERVICE` 的原地停留段，表示取货或卸货。

二者都会推进 `taskFinishTime`。连续调用时，后一段接在前一段后面。**它们只是安排轨迹，不会立刻让无人机飞到终点，也不会立刻扣掉整项任务的电量。**

## 七、advance：时间跳过去之后，位置和电量怎么更新

`advance(t)` 把所有无人机从旧的 now 更新到 t，最后才令 `now=t`。

如果正在充电，就增加 `(t-now)×CHARGE_RATE` 的电量，但最多充到容量。

如果有飞行或服务轨迹，对每个小段计算它与本次时间区间的重叠时长：

```cpp
double dt = max(0.0, min(t, leg.end) - max(now, leg.begin));
```

例如当前从 3 秒推进到 7 秒，某段在 5 到 8 秒发生，真正经过的部分只有 5 到 7 秒，所以 dt=2。

耗电按已经经过的比例计算：

```text
耗电 = 线段长度 × 重叠时长 / 线段总时长
```

这既更新无人机剩余电量，也计入 `energyUsed`。服务段首尾位置相同，长度为 0，因此不会耗电。

如果 t 已经超过该段结束时刻，位置就更新到终点；如果 t 落在线段中间，就按已经过的比例求当前位置。找到当前正在执行的小段后即可停止，不需要检查更晚的段。

这也是途中改道能够正确计算的原因：分配新订单之前，位置和电量已经更新到了当前事件发生的真实时刻。

## 八、evaluate：无人机和订单是否匹配，分数是多少

函数参数：

```cpp
double evaluate(int i, int j, double battery, Path &a, Path &b)
```

- i、j：无人机和订单编号。
- battery：本次用于检查的可用电量，通常是当前电量；补电判断时也可以传电池容量。
- a、b：引用参数，用来把取货、配送两段路线传回调用者。
- 返回值：可行时返回 f 分数，不可行时返回 -1。

判断顺序：

1. 重量超过最大载重，拒绝。
2. 用 A* 找出“当前点→取货点”的 a，以及“取货点→送达点”的 b。
3. 令 `E=a.len+b.len`。由于每米耗电 1，E 同时是配送任务的飞行耗电。
4. 算送达余裕时间 `s=deadline-now-E/SPEED-2*SERVICE`。找不到路或无法按时完成，拒绝。
5. 从送达点找到最近可达充电点，得到返程长度 back。
6. 若 `E+back+RESERVE` 超过可用电量，拒绝。

最后计算：

```text
f = 0.4 / (1 + 取货距离 / 10)
  + 0.4 / (1 + 送达余裕时间 / 30)
  + 0.2 / (1 + 配送耗电 / 30)
```

距离越短、余裕时间越小但仍可完成、耗电越少，分数越高。10、30、30 是固定归一化尺度；0.4、0.4、0.2 是当前权重。

代码中的 `max(0.0,s)` 用于把浮点误差造成的极小负余裕修正到 0。不是把真正超时的订单当成可行订单。

“预留返程电量”不等于“送完后一定马上充电”。它只是保证安全可达，实际后续任务仍由调度决定。

## 九、assignOrders：贪心分配的核心

每轮先设置 `di=0`、`oi=0`、`best=-1`，表示暂时没找到可行组合。

然后枚举无人机 i 和订单 j：只考虑 `IDLE` 或 `TO_HOTSPOT` 的无人机，以及满足 `waiting(j)` 的订单。调用 `evaluate()`，保留分数最高的一对及其两段路线。

如果最终 `di` 还是 0，就没有可分配组合，退出。

否则按顺序执行：

```cpp
beginTask(di, DELIVERY);
fly(di, first);
service(di, order[oi].pickup);
fly(di, second);
service(di, order[oi].delivery);
```

也就是：前往取货点 → 取货 → 飞往送达点 → 卸货。随后标记订单已分配，记录出发时刻，并加入配送完成事件。

外面的 `while(true)` 会再做一轮枚举。刚分配的订单、无人机不再参与，因此不会重复分配。同分时只接受严格更大的分数，按当前从小到大的循环顺序保留先遇到的组合。

这是逐对贪心，可能让某架无人机接走另一架无人机唯一能做的订单，因此不保证完成订单数最多。

## 十、parkDrones：补电和热点待命

函数按编号依次处理剩余的 `IDLE` 无人机。

### 1. 什么时候补电

以下情况需要尝试充电：

- 电量低于容量的 30%，或者低于安全余量。
- 没有充满电，并且存在按“满电”检查可以配送的等待订单。

由于 `assignOrders()` 已先执行，第二种情况主要用于让电量不足以接单的无人机主动补电。

找到充电点后，检查去充电点所需电量及安全余量。若不能安全到达，设为 `GROUNDED`；否则建立去充电点的轨迹和抵达事件。已经位于充电点时不用飞行，即使电量为 0 也可以开始充电。

“现在假设满电能做”只是补电判断，没有把真实充电时间提前算进该订单的送达时间。充满后仍要重新检查，订单可能已经来不及配送。

### 2. settled 为什么存在

已经抵达待命点的无人机暂时不再换热点，避免刚到一个地方，就因供给数改变而飞向另一个地方。下一次订单到达时，会重新开放空闲无人机的待命选择。

正在飞向热点的无人机也不会在这里反复换目标，因为该函数只处理 `IDLE`；但它仍可被 `assignOrders()` 改道接单。

### 3. 怎么计算区域分数

对于每个区域 k：

- q：取货点属于该区域，且到达时刻位于 `(now-WINDOW, now]` 的订单数。
- n：区域内其他空闲无人机数，加上正在前往这里待命的无人机数。
- path：当前点到该区域待命点的 A* 路线。

q 包括已经配送或无法配送的新增订单，因为它统计的是需求出现次数；未来订单不计入。n 不包括正在选择区域的无人机自己。

先排除不能安全“到待命点，再到充电点”的区域，再计算：

```text
g = 0.5 × (q / 5)
  + 0.3 / (1 + n / 3)
  + 0.2 / (1 + 待命距离 / 10)
```

需求越多、已有无人机越少、距离越近，分数越高。选中后立即修改无人机状态和目标，所以下一架无人机能看到更新后的供给数。

## 十一、handle：事件到了，具体修改什么

| 事件 | 修改操作 |
|---|---|
| `ARRIVAL` | 将空闲无人机的 `settled` 清除，允许重新选择热点 |
| `FINISH` | 记录订单完成时间，无人机设为空闲 |
| `REACH_CHARGER` | 切换为充电状态，按缺少电量计算充满时刻，加入 `CHARGED` 事件 |
| `CHARGED` | 电量设为容量，无人机设为空闲 |
| `REACH_HOTSPOT` | 无人机设为空闲，`settled=true`，清除目标区域 |

订单到达时没有单独设置 `arrived` 字段，因为 `waiting()` 直接比较订单到达时刻和 now。

除订单到达外，事件处理会清除已经结束的旧轨迹。抵达时的位置和途中耗电已经由前面的 `advance()` 更新，不需要在这里再飞一遍或扣一次电。

## 十二、main：输入、事件循环和输出

### 1. 输入

第一行是：

```text
X Y Z B C R N M horizon
```

接着依次读入禁飞格、充电点、区域、无人机、订单。订单读入后，立即把它未来的到达事件加入队列。

这里提前读完全部输入只是离线仿真的实现方式；评分仍然通过 `arrival<=now` 排除未来订单。

`ios::sync_with_stdio(false)` 和 `cin.tie(0)` 用来减少流输入输出的额外开销。本程序统一使用 `cin/cout`。`fixed << setprecision(3)` 让时间、电量等小数输出三位小数。

### 2. 事件循环

循环的主要顺序是：

```text
处理 now 时刻的全部有效事件
    ↓
assignOrders：分配订单
    ↓
parkDrones：补电或待命
    ↓
丢弃队首失效事件
    ↓
advance：把时间推进到下一个事件
```

第一次 now 为 0，因此即使第一张订单尚未到达，也可以先安排补电或去待命点。之后每次 `advance()` 先更新位置和电量，再进入下一轮处理相应事件。

同一时刻的事件一起处理，是为了让“恰好完成配送的无人机”和“此时新到的订单”同时参加下一轮分配，避免先处理谁就让谁占便宜。

如果队列为空，或下个事件超过 horizon，就只更新到 horizon 并结束。尚未完成的任务不会提前算作完成，电量也只累计到实际截止时刻。

### 3. 输出

`assign ...` 表示某时刻分配了一张订单，输出预计完成时间。每张订单最后还会输出实际 `takeoff` 和 `finish`。

最终统计：

| 字段 | 口径 |
|---|---|
| `arrived` | 截止 horizon 已到达的订单数 |
| `completed` | 已实际收到完成事件的订单数 |
| `energy` | 所有无人机实际飞行的耗电，包含配送、去充电点、热点移动 |
| `avg_time` | 已完成订单的平均“完成时刻－到达时刻”，包括等待、取货、卸货 |

`finish=-1` 可能表示订单未分配，也可能表示尚在配送，需要结合 `takeoff` 看。未完成订单不进入平均配送时间的分母。

## 十三、拿一张订单把全过程串起来

假设没有障碍，无人机在 `(0,0,0)`，电量 10，载重足够；充电点也在 `(0,0,0)`。订单在 0 秒到达，取货点 `(1,0,0)`，送达点 `(3,0,0)`，最晚 10 秒送达。

可行性检查得到：

```text
取货距离 a.len = 1
配送距离 b.len = 2
配送任务耗电 E = 3
总耗时 T = 1 + 1 + 2 + 1 = 5 秒
送达余裕 s = 10 - 0 - 5 = 5 秒
从送达点回充电点需要 3 单位电量
任务所需安全电量 = 3 + 3 + 2 = 8 <= 当前电量 10
```

所以可以分配，并生成 5 秒的配送完成事件。轨迹为：

| 时段 | 操作 | 该段耗电 |
|---|---|---:|
| 0～1 秒 | 飞到取货点 | 1 |
| 1～2 秒 | 取货 | 0 |
| 2～4 秒 | 飞到送达点 | 2 |
| 4～5 秒 | 卸货 | 0 |

时间推进到 5 秒后，无人机位于送达点，电量是 7。处理 `FINISH` 事件，订单完成时间设为 5，无人机变为空闲，随后才能参与下一轮分配。

如果中间 2.5 秒有另一张订单到达，程序会先更新这架无人机的位置和电量；但它仍处于 `DELIVERY`，不会中断现有配送去接新单。

## 十四、附带示例的输出怎么理解

同目录的 `example.in` 配合本版本运行，输出末尾为：

```text
arrived=6 completed=3 energy=32.000 avg_time=10.000
```

已完成订单是 1、3、6：

| 订单 | 到达时刻 | 出发时刻 | 完成时刻 | 从到达到完成 |
|---|---:|---:|---:|---:|
| 1 | 0 | 0 | 8 | 8 |
| 3 | 2 | 8 | 15 | 13 |
| 6 | 20 | 20 | 29 | 9 |

所以平均配送时间为 `(8+13+9)/3=10` 秒。

订单 4 超载，订单 5 时间窗不足；订单 2 也没有得到可行分配。**未完成不一定表示订单本身在所有情况下都无法配送，也可能是当前贪心决策和可用无人机状态的结果。**

## 十五、这份代码目前的简化和限制

- 一架无人机一次执行一单，配送、飞往充电点和充电期间不参与新单匹配。
- 地图不变，速度不变，耗电仅与距离成正比；没有模拟天气、载重对耗电的影响。
- 充电点始终可用，不模拟排队，也没有多机避碰。
- 归一化尺度和权重直接写在公式里，尚未通过对比实验选优。
- 没有未来任务预约、订单交换、任务取消或重新分配。
- 反复枚举组合并跑 A*，适合小规模演示。输入保证合法，程序没有复杂的数据校验。

如果要修改业务策略，优先改 `evaluate()` 和 `parkDrones()`；如果要修改地图找路规则，再改 `astar()`。先把这几个部分的职责区分清楚，就能顺着事件循环读懂整个程序。
